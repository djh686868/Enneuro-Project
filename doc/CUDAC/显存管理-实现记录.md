## 二、阶段2：内存池

### 2.1 交付物

**无新增文件**，全部落在 `code/eneuro/utils/dev_memory.py`；`dev_memory.cu`（C 层）**一行未改** ——
内存池是 Python 层的实现细节，直接复用阶段1 的 `ene_mem_alloc/free`。

新增内容：`_size_class()` 分桶函数、`DeviceAllocator` 的池化逻辑与三个新参数、
`trim()` / `free_blocks` / `DeviceBuffer.capacity`、`stats()` 的池字段。

### 2.2 分桶策略：对设计的一处修正

| 区间 | 原设计 | 实际实现 | 内部碎片 |
|------|--------|----------|----------|
| ≤ 4 KB | 256 B 步进 | 同 | ≤ 255 B |
| 4 KB ~ 1 MB | 2 的幂分桶 | 同 | ≤ 2x |
| > 1 MB | 直通，不进池 | **按精确大小分桶，进池** | 0 |

**修正理由来自实测**（`pool=False` 时一次 malloc+free 的耗时）：

| 块大小 | 不池化 (us) | 池命中 (us) | 提速 |
|--------|-------------|-------------|------|
| 4 KB | 4.36 | 2.42 | 1.8x |
| 64 KB | 4.59 | 2.45 | 1.9x |
| 1 MB | 5.80 | 2.48 | 2.3x |
| **4 MB** | **300.09** | **2.41** | **124.7x** |

驱动的 caching allocator 对 ≤ 1 MB 的块缓存得很好（约 5 us），但 **4 MB 的块每对
malloc/free 要 300 us**。如果按原设计把 > 1 MB 直通，那么典型尺寸的激活张量
（常在 1 ~ 16 MB）每个训练步都要付这 300 us —— 在 10 ms 级的训练步里就是 3%。

「大块长期占显存」这个原设计想解决的问题，改用 `pool_max_bytes` 上限 +
`trim(older_than=)` 解决，比一刀切更精细。需要旧行为时传 `pool_max_block=1<<20`。

### 2.3 新增 API

| 参数 / 成员 | 说明 |
|-------------|------|
| `pool=True` | 关掉即退化为阶段1 的直通分配（每次 `cudaMalloc`） |
| `pool_max_block=None` | 超过此容量不进池；传 `1<<20` 即原设计行为 |
| `pool_max_bytes=None` | 池中空闲字节上限，超出按 **FIFO** 驱逐最旧的 |
| `trim(older_than=None)` | 归还池中空闲块给驱动；`older_than=30` 只归还已空闲 30 s 以上的 |
| `free_blocks` | 当前池中空闲块列表 |
| `DeviceBuffer.capacity` | 实际占用显存字节数（≥ `nbytes`，差额是内部碎片） |
| `stats()` | 新增 `pool_hits` / `pool_misses` / `hit_rate` / `free_blocks` / `free_bytes` / `largest_free_block` / `fragmentation` / `evicted_blocks` / `trimmed_blocks` / `free_classes` |

### 2.4 四个关键实现细节

1. **复用时不改旧 `_BlockInfo`，而是新建一个**。若就地把旧块信息改回可用，
   旧的 `DeviceBuffer` 句柄会重新「活过来」并指向新块 —— 典型悬垂别名 bug。
   测试 [6] 专门验证了「地址被复用后旧句柄仍然报错」。
2. **快路径完全不碰 CUDA**：命中时只有一次 dict 查找 + pop + 新建元数据对象。
3. **不在持锁时调用 `cudaFree`**：`_release` 在锁内只做记账与挑选，
   真正 free 放到锁外；`trim` 与驱逐同理。
4. **`_BlockInfo` 用 `eq=False`**：让 `list.remove` 走身份比较，
   避免字段相同的块被误删。

### 3.3 被测试抓出的一个真 bug

`cuda_ops.stream_ptr()` 原来是这样：

```
if cp is None: return 0        # cupy 不可用 -> 直接把流丢掉
```

而 cupy 不可用正是方案A 的典型场景。后果是 **kernel 全部落在默认流上**：
双缓冲永远不可能重叠，而且「在自定义流上跑算子」的测试也只是假通过。
已修成「int 原样透传」（cupy 的流对象仍走 `.ptr`），不改变方案B 的行为。

### 3.4 同步语义的变化（兼容性）

| 接口 | 阶段1/2 行为 | 阶段3 之后 |
|------|--------------|------------|
| `upload` / `download` | 同步（返回即完成） | **语义未变**（保持向后兼容） |
| `upload_async` / `download_async` | — | 只入队；用前必须 `sync()` 或依赖同流顺序 |
| 跨流 | 不涉及 | 需调用方用事件显式建立依赖 |

异步是**新增**接口而非改默认行为，所以阶段1/2 的代码不会静默变错。

### 3.6 这一阶段纠正的两个认知与两个测量坑

**认知一：异步本身不提高纯传输带宽。** 异步 pinned（12.0 ~ 12.3）与同步
pinned（11.8 ~ 12.4）基本持平。异步的价值是「传输能与计算重叠」，不是「传得更快」。

**认知二：带宽提升来自 pinned，不来自异步。** pageable 8.2 ~ 10.6 →
pinned 11.8 ~ 12.4，约 1.2 ~ 1.4x。

**测量坑一：标定 kernel 耗时前必须先预热一次 launch。** 首次 launch 会加载 CUDA
模块（本机约 20 ms），不预热会把这一性开销平均进 20 次循环，得出「kernel 要 1 ms」
的假数据（真实值约 17 ~ 23 us，相差约 50 倍）。

**测量坑二：单次均值会被抖动抬高。** 改成多轮取最快一轮（min-of-rounds）后，
同一场景的重复测量才稳定。`bench_dev_memory_pipeline.py` 与
`test_dev_memory_async.py` 都已按这两条修正。

### 3.7 当时留下的限制

- 池的跨流复用未防护（阶段 5）；
- 只有一条 copy 流，多个 chunk 的拷贝彼此串行 → 重叠收益上限是
  `(拷贝+计算) / max(拷贝,计算)`，本机实测约 **1.3x**；
- `download_async` 要求 pinned 目标（刻意的：pageable 目标的异步 D2H 实际不会异步）；
- 未实现 `__cuda_array_interface__`（阶段 4）。

### 4.3 为什么要「租约」

`cp.ndarray` 只记得一个裸指针，它**不**引用我们的 `DeviceBuffer`。一旦句柄被 GC 或
显式归还，块回到池里并被下一个 `alloc` 复用，那个数组就会静默地读到别人的张量 ——
错得没规律、不错也不报错，属于最难查的一类问题。所以这必须用机制堵住，而不是写成
文档注意事项。

试过并否掉的两个方案：

| 方案 | 结果 |
|------|------|
| 直接在块上存 `lease` 对象 | 形成「块 → 集合 → lease → 块」的引用环，`lease` 永远死不了 |
| `WeakSet` | 能自动摘牌，但拿不到「最后一个视图消失」这个**回调时机**，无法触发回收 |

最终方案是**借用 cupy 自己保证的引用链**当探针：

```
cp.ndarray ──► MemoryPointer ──► UnownedMemory ──► owner(=_Lease)
                  .mem              ._owner
```

（属性链已实测：`arr.data is memptr`、`arr.data.mem is mem`、
`arr.data.mem._owner` 就是我们的 `_Lease`。）

再在块上登记 `weakref.ref(lease, _LeaseWatch(alloc, info))`：弱引用目标一死，
回调摘掉租约；最后一个租约消失时，才把块真正入池或还驱动。

当时代码里用 `UnownedMemory` 的关键理由是**所有权不转移**：它被设计成「别人的内存」，
只负责把 `owner` 保活、绝不 `free`，所以释放责任仍在分配器手里。

### 4.4 交付时修掉的一个边界 bug

`force=True` 释放后显存可能立刻被复用；若新块也进入延迟表，**旧租约死亡时会按 `ptr`
把新块误弹出去**并提前归还。已改成按对象身份校验：

```python
if self._pending_release.get(info.ptr) is not info:
    return
```

这与阶段2「`_reuse_info` 新建 `_BlockInfo`」是同一类「防悬垂别名」问题。

| [5] 租约保活（句柄先死 / 视图后死 / 多视图 / 延迟回收后回池） | 16 |
| [6] 租约未清时释放报错、`force=True` 放行、双重释放仍检出 | 6 |
| [7] 混合模式：cupy 输入 + 池 workspace | 7 |
| [8] `strict_interop` 开关、主机回退模式 | 4 |
| [9] 越界保护：`shape` 用 `nbytes` 而非桶容量 | 2 |

关键实测：

| 指标 | 结果 |
|------|------|
| cupy 零拷贝一致性（4 个方向） | max\|diff\| = **0.0e+00** |
| 句柄删除后视图仍可读 | 块未回池（`free_blocks=0`），进 `deferred_blocks` |
| 最后一个视图死亡 → 块回池 | `deferred=0`、`free_blocks=1` |
| 混合模式热路径（n=4096，400 次 kernel） | 每轮 15.3 us、分配增量 0、`cudaMalloc` 增量 0 |
| 非法 CAI 输入拦截 | dtype / 连续性 / 空指针 / version<3 全部拦住 |

### 4.6 当时暴露的边界

- 「瞬时借出」无法跟踪（协议限制），只能靠 `strict_interop` 或约定；
- `close()` 不等待外部视图：有视图存活时打印一行警告然后把显存还掉；
- 跨流复用仍未防护（阶段 5）。

## 五、阶段5：多设备与并发（已完成）

> 5.1 ~ 5.10 是**动手前写的计划**（原样保留，便于对照）；
> 5.11 ~ 5.13 记录**实际落地结果**。当前行为以 `显存管理.md` 为准。

### 5.1 阶段5 要收的口子

全部对应 `显存管理.md` 第九节列出的已知限制：

| 编号 | 现状缺口 | 阶段5 目标 |
|------|----------|------------|
| FR-8.1 / FR-8.2 | 分配器不校验「块所在设备 == 当前设备」 | 跨设备误用**必须报错**，信息含两个设备号 |
| FR-8.3 | 池未按设备隔离 | 每设备独立实例（进程级 `get_allocator(device)` 工厂） |
| FR-7.1 | 块不记录「最后被哪个流用过」 | 每块记录 `last_stream`，跨流复用前用事件建立依赖 |
| FR-7.3 | 跨流复用无防护，安全前提是单流 | 默认关闭；开启后靠事件防护，**不做主机同步** |
| FR-11.1 | C 侧计数非原子；锁未按设备划分 | 计数改进程内原子；锁按 allocator（即按设备） |
| FR-11.3 | `_finish_deferred` 可能在 GC 线程执行 | 复查锁序，确保不在持锁时触发 Python 回调 |
| FR-9.2 | 无越界哨兵 | `debug=True` 时头尾写魔术字，`release` 时校验 |

### 5.2 第一优先级：C 层的设备状态是「进程全局」

开始规划前先确认了一个**当前就存在**的隐患：

```c
static int g_device = -1;            // 进程级静态，不是线程局部
int ene_mem_init(int device) {
    ... cudaSetDevice(device);
    g_device = device;               // 谁最后 init，全局就认为谁是当前设备
}
```

后果：同一个线程里创建 `DeviceAllocator(0)` 和 `DeviceAllocator(1)` 之后，
`g_device` 变成 1，而 CUDA 的 current device 也停在 1 —— 此时**再让 allocator 0
去分配，显存会静默落在 1 号卡上**。单卡环境完全发现不了，双卡就是静默算错。

所以阶段5 的第一件事不是加功能，而是把设备状态从「进程全局隐式」改成
「每分配器显式」：

| 改动 | 内容 |
|------|------|
| C 层 | `g_device` 改为 `ENE_TLS int g_current_device`（CUDA 的 current device 本就是线程局部的） |
| C 层 | 新增 `ene_mem_set_device(int)` / `ene_mem_current_device()`；后者返回线程局部缓存，**不调 CUDA**，O(1) |
| C 层 | `ene_mem_init(device)` 只做「校验 + `cudaSetDevice` + 记录」 |
| Python 层 | `DeviceAllocator._bind_device()`：触碰设备资源前确保当前设备是自己那张卡；`self._bound` 缓存避免重复调用 |
| Python 层 | 分配 / 释放 / 传输 / 流 / 事件 / pinned 六个入口统一先 `_bind_device()` |

开销：缓存命中时只有一次 Python 判断；未命中时一次 `cudaSetDevice`（< 0.1 us），
相对一次 kernel launch（约 10 us）可忽略。

### 5.3 跨设备强制校验

`device_ptr(DeviceBuffer)` 增加一项校验（当前设备优先用 cupy 的 `getDevice()`，
cupy 不可用时用 `ene_mem_current_device()` 的线程局部缓存）：

```
ValueError: 块 'a' 在第 1 张卡，当前设备是 0（不会隐式拷贝，请手动搬到对应设备）
```

配套开关：`DeviceAllocator(strict_device=True)`（默认开）。热路径若想省掉这次
判断，可关掉但**不建议**——代价是一次 ctypes 调用，收益不到 2%。

### 5.4 跨流复用保护

难点在于：kernel 是 `CudaOps` 直接拿裸指针下发的，**分配器看不到这次使用**。
所以不能只靠「记录 allocator 自己的传输流」，必须有一个声明通道。

方案（三条路，取第三条）：

| 方案 | 结论 |
|------|------|
| 让 `CudaOps.dev` 必须传 allocator | ❌ 破坏 D3「池与算子解耦」 |
| 让调用方手动 `buf.mark_stream(s)` | ⚠️ 能用但容易漏，默认不算安全 |
| `CudaOps.dev` 对每个对象尝试回调可选的 `_ene_note_stream(stream)` | ✅ 解耦、零成本、漏用时不报错但保护仍在 |

具体机制：

1. `DeviceAllocator(cross_stream_reuse=True)` 开启后，`DeviceBuffer._ene_note_stream(s)`
   把 `info.last_stream = s` 记下来（关闭时该方法直接 return，零开销）；
2. `release()` 时若 `last_stream` 非 0，块不立即入池，而是进 `_stream_guard`，
   并对该流记一个**惰性创建**的事件；
3. `alloc(..., stream=t)` 取到带 guard 的块时，`ene_mem_event_wait`（或
   `cudaStreamWaitEvent`）让 `t` 等这个事件 —— **主机不阻塞**；
4. 事件随块惰性创建、随块销毁（`close()` / `_free_native`）。

默认关闭（对齐 FR-7.3）：关闭时既不记录也不等待，行为与现在完全一致。

### 5.5 线程安全

| 改动 | 内容 |
|------|------|
| C 侧计数 | `g_alloc_calls++` 等 5 个计数器改为原子（MSVC `InterlockedIncrement64` / GCC `__atomic_add_fetch`） |
| 锁粒度 | 维持 per-allocator 锁（多卡各有各的锁，已等价于「按设备划分」） |
| 死锁复查 | `_finish_deferred` 可能在 GC 线程被调用：保持「锁内只记账、锁外 free」；不在锁内触发任何 Python 回调 |
| 设备绑定 | `cudaSetDevice` 本身是线程局部的，多线程各自 `_bind_device()` 互不干扰 |

### 5.6 可选：debug 越界哨兵（FR-9.2）

`DeviceAllocator(debug=True)` 时每块头尾各留 64 B 并写魔术字，`release` / `trim` 时校验，
`stats()` 输出 `corrupted_blocks`。会改变 `capacity` 与对齐，因此只在 debug 模式启用；
关闭时零开销（一条 `if`）。

### 5.7 验收标准（草案）

| 项 | 方法 | 通过标准 |
|----|------|----------|
| 多卡交替 | 两个 allocator（device 0 / 1）交替 alloc + upload + download，各 1000 轮 | 无错误、数据正确；`ene_mem_current_device()` 与 allocator 所在卡一致 |
| 设备错用 | 把 device 1 的块喂给 device 0 的 kernel | 抛 `DeviceError`，信息含 `0` 与 `1` |
| 跨流复用（开） | A 流写 → `release` → B 流取用，B 流计算结果 | 结果正确；**主机侧无 `cudaDeviceSynchronize`** |
| 跨流复用（关） | 同上但不开开关 | 行为与现状一致（单流假设），不做任何额外同步 |
| 并发 | 8 线程 × 10 万次 alloc/release | `live_blocks=0`，C 侧计数与 Python 计数一致（无少记） |
| 不回归 | NFR-1 / NFR-3 + 阶段1–4 全部套件 | 分配开销 < 5 us；稳态 `cudaMalloc` = 0；179 项全通过 |
| 无卡环境 | 屏蔽 CUDA | 全部相关用例跳过并给出明确提示，不崩 |

### 5.8 风险与对策

| 风险 | 对策 |
|------|------|
| `cudaSetDevice` 调用频繁 | 线程局部缓存 + 只在变化时调用 |
| 每块一个 event 的句柄开销 | 惰性创建，只在跨流复用时创建；关闭开关时零开销 |
| GC 回调线程里取锁 | 延续「锁内只记账、锁外 free」；避免在锁内触发 Python 回调 |
| debug 哨兵改变 `capacity` | 独立容量计算路径 + 显式 `debug` 标志 |
| **手头只有单卡** | 多卡用例需借用设备或 CI；单卡上可先用「伪造 device_id」验证校验逻辑本身 |

### 5.9 明确不在阶段5 范围

- 碎片整理 / 显存超分 / 换出到主机；
- 多进程显存共享；
- 多卡 P2P / NVLink 通信；
- 跨设备**自动拷贝**（FR-8.1 明确要求报错而不是偷偷搬）。

### 5.10 工作量

C 层约 60 行（设备状态 + 原子计数）、Python 层约 250 行（绑定、校验、跨流保护）、
新测试约 150 行。整体仍属「中」，但**多卡验收依赖硬件**，实际排期取决于能否拿到双卡环境。

### 5.11 实际落地

实际改动量：C 层 `488 → 537` 行（+49），`dev_memory.py` `1603 → 1909` 行（+306），
新增测试 `test_dev_memory_multidev.py`（58 项）。

| 层 | 改动 |
|----|------|
| C 层 | 新增 `ene_mem_set_device` / `ene_mem_current_device` / `ene_mem_cached_device`；`g_current` 改为 `ENE_TLS`；5 个计数器改 `std::atomic<unsigned long long>`（用 `std::atomic` 而不是 `Interlocked*` / `__atomic_*`，一处代码同时适配 MSVC 与 GCC） |
| Python 层 | `strict_device` / `cross_stream_reuse` / `debug` 三个构造参数；`_bind_device()` 用于 12 个设备入口（**每次都问 C 层，判重在 C 层的线程局部 `g_current`**）；`current_device()` / `cached_device()`；`DeviceBuffer.assert_current_device()` / `_ene_note_stream()` / `allocator`；`MemoryCorruptionError` |
| 跨流 | `_BlockInfo.last_stream` / `guard_event`；`_guard_stream()` / `_take_guarded()` / `_sweep_stream_guard()`；`alloc(stream=)` |
| 哨兵 | `_BlockInfo.base_ptr` / `physical` / `alloc_ptr` / `alloc_bytes`；`_write_guards()` / `_check_guards()` / `_raw_copy()` |
| 算子层 | `_prepare_dev_args()`：每个 allocator 只查一次设备，并顺带记录流（开关关闭时零开销） |

与计划的两个偏差：

1. **设备校验放在 `CudaOps.dev()` 而不是 `device_ptr()`**。
   计划里想改 `device_ptr`，但那样每次 `ops.dev` 会做 4 次 `cudaGetDevice`，
   而且会破坏 FR-5.2「取指针是零成本」的承诺。改成在 `dev()` 里按 **allocator 去重**
   只查一次，且 `device_ptr` 保持纯取指针。
2. **哨兵读写必须先经 C 层**（见 5.12）。

### 5.12 实现时抓出的两个坑

**坑一：设备状态是「进程全局」**（在 5.2 里已预判，实测完全坐实）。
`g_device` 是 `static`，`ene_mem_init` 会同时改 `cudaSetDevice`。同一线程先后创建
两个不同卡的 allocator，前一个的后续分配会静默落在后一张卡上。已改为线程局部 +
每分配器显式绑定。

**坑二（计划里没想到）：设备内存不能由主机 `ctypes.memmove` 直接写。**
第一版 `_write_guards()` 写的是：

```python
ctypes.memmove(info.base_ptr, _GUARD_MAGIC, _GUARD_BYTES)   # 错
```

主机回退模式下没问题（那是真的主机内存），但在真 GPU 上直接段错误：
`OSError: access violation writing 0x705600000`。哨兵的读写必须走
`ene_mem_upload/download`（即 `cudaMemcpy`）。

连带引出一个 FR-11.2 问题：池命中时 `_reuse_info()` 是在**持锁**状态下调用的，
而 `ene_mem_upload` 内部会 `cudaStreamSynchronize`。已把哨兵重写移到锁外：
先在锁内取块并新建 `_BlockInfo`，出锁后再写哨兵、再登记。

第三个较小的问题：`_pool_or_free` 重写时把 `if info.cls is not None` 改成了
`recycle = info.cls is not None and ...`，丢掉类型收窄，静态检查报 `BucketKey | None`。
已恢复成直接 `if` 判断。

**坑三（画时序图时对照代码才发现的）：`_bind_device` 一度用 Python 侧缓存做短路。**
第一版是 `if self._bound == self._device: return`。单看没错，但 `_bound` 是**每个
allocator** 的字段：同一线程里 A(0) → B(1) → A(0) 交替时，A 的 `_bound` 还是 0，
而线程早已被 B 绑到 1。此时 A 跳过绑定 → 分配又静默落到 1 号卡 —— 正是阶段5 要修的那个 bug
换了个位置复发。已改成每次都调 `ene_mem_set_device`，判重放在线程局部的 C 层（命中时
只比较一个 int）。并在 `test_dev_memory_multidev.py` 里加了一条计数用例：
连续调两次 `_bind_device()`，必须观察到**两次** C 层调用。

**坑四（用户追问「清扫到底在哪」时查出的）：`alloc` 路径根本没清扫。**
设计里写的是「`alloc()` 与 `sync()` 都会查询守卫事件」，但代码里只有 `sync()` 调了
`_sweep_stream_guard()`。`alloc_bytes` 只有在**同桶**时才通过 `_take_guarded()` 取走
守卫块；如果后续一直分配别的尺寸，已完成的守卫块就永远挂在表里 —— 那部分池容量
等于永久不可用（且 `trim()` 也不会碰它）。已补在 `alloc_bytes` 快路径之前：

```python
if self._stream_guard:          # 关闭跨流复用时恒为空，零成本
    self._sweep_stream_guard()
```

补上后原有 [5] 组的「必须插入事件等待」反而失效了 —— 因为清扫先把已完成的块放回池，
走的是另一条同样正确的路径。排查后发现根因在测试：4 MB 的 kernel 三个缓冲共 12 MB，
完全装在 24 MB 的 L2 里，单次只要 **2.4 us**，而 Python 入队一次要约 **30 us** ——
入队比执行慢，队列永远是空的，事件自然已完本。改成 64 MB × 8 次（受显存带宽限制，
单次约 0.9 ms）后才稳定复现「事件未完成 → 插入等待」这条路径。

### 5.14 已知遗留

- **真实双卡未验证**：本机只有 1 张卡。校验逻辑用「伪造 device_id」验证过了，
  但「两个 allocator 各自真正落到不同卡上」的用例需要双卡环境；

- debug 哨兵会让每块多占 512 B，仅调试期使用。
